# FitFlow — Reliability & Trust Audit
**September 29, 2026 · prepared for sell-readiness review**

This is the honest list: everything found by probing the production database, the
sync history, the security posture, and the codebase — plus everything that
cannot be verified from outside and therefore cannot be claimed with certainty.
Ordered by how much each item threatens a customer's faith in the numbers.

---

## CRITICAL — numbers are wrong or exposed today

### C1 · Currency mixing: CAD and USD are summed as if equal
The payments table holds **955 CAD payments ($886,994) and 557 USD payments
($466,912)**. All Meta ad spend is USD. The metrics engine has **no currency
handling** — it sums cents across currencies and formats everything as USD.
Consequence: every revenue figure, ROAS, and LTV that touches a mixed period is
silently wrong (a CAD dollar counted as a USD dollar, ~35–40% distortion on the
CAD share). This is the single largest threat to trust in the product.
**Fix**: pick one reporting currency (recommendation: **CAD** — the business is
Canadian and CAD is the payment majority), convert at a stored per-day rate,
show original currency on each payment row, and have the engine refuse to sum
unconverted amounts (type-level guarantee). Requires a one-question sign-off:
report in CAD or USD?

### C2 · The database has an unlocked side door (RLS disabled on all 14 tables)
Supabase exposes every `public` table through its REST API, and **row-level
security is disabled on all 14 tables** (confirmed by Supabase's own security
advisor). Anyone holding the project's "anon" API key — a key Supabase treats
as publishable — can read every table over HTTPS: client PII, payments, and
the **settings table, which stores the GHL, Meta, and Stripe keys in
plaintext**. The app's login protects the app; it does not protect this door.
The anon key has never been published anywhere, which is why this has not been
exploited — but "nobody has the key yet" is not a security model.
**Fix (no app impact — the app connects as the table owner, which bypasses
RLS)**: enable RLS with no policies on all tables (deny-all for the API), then
encrypt stored credentials at rest, then rotate all three provider keys.

## HIGH — will break or mislead soon

### H1 · Appointments data stale since Sept 17 (12 days) — still unfixed
The budget-limited GHL sync has completed 0 full cycles in 19+ runs; the
appointments phase is never reached. Show rates and no-show/rebook to-do lists
are frozen; the nightly mirror-vs-GHL reconciliation has **never executed**.
**Fix**: run `npm run sync:now` today; ship the cycle-reorder (tracked
pipeline's appointments before untracked mirrors); upgrade to Vercel Pro so
hourly syncs make full cycles routine. All three are already specced.

### H2 · Meta token may be on a 60-day fuse — expiry unknown
If the token generated Sept 1 was 60-day rather than "never," Meta spend dies
silently around **Oct 31**. The stale banner would notice a day later, but the
app should know beforehand.
**Fix**: nightly token self-check (Meta's debug endpoint returns expiry) with a
7-day advance warning in sync health and the digest.

### H3 · No database backups (Supabase free tier)
One bad migration or accidental delete is unrecoverable. Backups/PITR are a
paid Supabase feature; nothing else copies this data anywhere.
**Fix**: nightly `pg_dump` to a private store (or Supabase Pro). A business
tool a CEO relies on cannot have zero recovery story.

### H4 · Credentials at rest are plaintext (part of C2 but stands alone)
Even with RLS closed, the settings table should not hold raw provider keys.
**Fix**: AES-GCM encryption with a key held only in Vercel env
(`CREDENTIALS_KEY`); masked everywhere, decrypted only server-side at call
time; migration re-encrypts existing rows; rotate providers after.

## MEDIUM — quality-of-trust issues

- **M1 · Winter clock bug (Nov 2 onward)**: the daily dispatch fires ~13:28 UTC
  = 7:28am in summer (MDT) but **6:28am in winter (MST)** — before the ≥7am
  send guard, so every digest would skip all winter on the free plan's single
  daily run. Fix: widen the guard to ≥6am local or move the cron to 14:00 UTC.
- **M2 · Staleness is tracked per source, not per data family**: a "partial"
  GHL run reads as fresh while appointments age (how H1 hid). The family-level
  staleness fix is specced; ship it.
- **M3 · 466 payments carry a null class**: these are the deliberate "not
  cash" rows (failed/refunds/plan artifacts), but null-as-meaning is fragile.
  Make it an explicit `excluded` class and show the excluded total in the
  Revenue tab footer so the books visibly reconcile to Stripe.
- **M4 · Login rate-limit is per-serverless-instance** (in-memory): resets on
  cold starts. Acceptable for a shared password; noted for the record.
- **M5 · Dispatch skip reasons are empty `{}`** in sync_runs — observability
  gap, already specced in the cycle-reorder prompt.

## UNCERTAINTIES — cannot be verified from outside; each needs a human check

1. Meta token expiry type (60-day vs never) — check Business Settings, or ship H2 and let the app answer.
2. Stripe webhook: registered in the Stripe dashboard or not? (Nightly reconcile currently covers it either way.)
3. Resend key / sending domain: emails still preview-only? Digests currently record "skipped."
4. Anthropic key: added or not — insight cards and Ask are unverified against a live key.
5. GHL contract values (`monetary_value`): CAD or USD? Affects LTV:CAC under C1's fix.
6. Business timezone: `America/Edmonton` assumed — confirm this matches how Jake thinks about "the week."
7. Real-device testing: the app has been verified in headless Chromium screenshots only — Safari/iPhone (how Jake will actually open it) has never been formally checked.
8. Scale behavior: 3,200 contacts today; tables/queries are unmeasured at 20k+ contacts.
9. GHL API drift: the schema-coercion guard catches shape changes, but GHL can change behavior undetectably (e.g., silently omitting records).
10. Vercel plan status: everything above assumes still-free; several fixes get easier on Pro.

## SELL-READINESS — gaps between "Jake's tool" and "a product customers buy"
Single-tenant by design today (one deploy + one database per customer; no org
model), shared password instead of per-user accounts + audit trail, no uptime
monitoring or status page, no onboarding flow a stranger could complete
unaided, no data-processing/privacy policy for client PII, no support runbook.
None of this blocks Jake; all of it precedes selling to a second customer.
